# B70: llama.cpp SYCL — MTP4 + 128K + KV q8_0 (5 Text + 3 Vision Full Pass) — 2026-08-21

**最终定稿报告**。这是 Intel Arc Pro B70 上 **MTP 满配 + 满上下文** 的极限验证，首次以 MTP4 + 128K 完成 **5 文本测试全通（5/5）** + **3 真实图像测试**。

## 配置（当前最佳 / 极限配置）

- **硬件**：Intel Arc Pro B70 (32GB, Battlemage G31)，`pcie_aspm=off`
- **后端**：容器 `b70-qwen27b-ggmlorg-mtp` @ 18080/v1
- **模型栈**（全 ggml-org）：
  - 主模型：Qwen3.8-27B-Q4_K_M.gguf（18.9 GB）
  - mmproj：mmproj-Qwen3.8-27B-BF16.gguf
  - MTP Draft：mtp-Qwen3.8-27B-BF16.gguf（≈5.9 GB）
- **关键参数**：
  - `--ctx-size 131072` (128k)
  - `--cache-type-k q8_0 --cache-type-v q8_0`
  - `--spec-type draft-mtp`
  - `--spec-draft-n-max 4 --spec-draft-p-min 0.1`
  - `--n-gpu-layers 999 --flash-attn on`
- **视觉**：mmproj 参与 OCR / 截图理解

完整启动命令见 `examples/qwen27b-server.sh`（已同步当前配置）。

- MTP4 + 128K 在 decode 上与 MTP3/96K 接近（36~41 vs 32~35 t/s），但**能稳定跑满 128K 上下文**。
- **KV q8_0 是 MTP + 大上下文的生命线**：draft 5.9 GB + 主模型 18.9 GB + 128K KV，只有 q8 才能塞进 32GB B70（历史 fp16 KV 全部在 t4 OOM）。
- vs vLLM-MTP（单发 83~112 t/s）：llama.cpp 慢 3~6×，但 **B70 上唯一能 dsh 全通的稳定后端**（vLLM-MTP t5 崩 2/2）。

## 三、最终结论（盖棺定论）

1. **MTP4 + 128K + KV q8_0 是 B70 上 MTP 满配 + 满上下文的顶点配置**。
   - 文本 5/5 全通 + 视觉可用。
   - TTFT 极低，decode 36~41 t/s，agent 长链 acceptance 0.50+ 可用。
   - KV q8_0 是唯一让 128K + MTP 稳定的关键。

2. **llama.cpp 是目前 B70 上唯一能稳定跑完整 dsh agent 任务的后端**（vLLM 在长链 t5 易崩）。

3. **视觉能力**：质量达到高阶水平（与双卡 27b 一致），但速度较慢，适合对质量要求高于速度的场景。

4. **单位数 OCR 是 Qwen3.8 全家固有硬伤**（跨后端共同问题，需裁剪放大复核）。

5. **推荐状态**：当前配置为 Arc B70 的**最佳/最终推荐配置**。后续若要更高性能，可考虑 vLLM 或降低上下文，但牺牲稳定性和上下文长度。

## 与 vLLM-MTP 的速度差异分析（为什么 vLLM 看起来快很多）

在同为 MTP4 + 128K 的配置下，vLLM-MTP 在部分任务上的解码速度明显高于本配置的 llama.cpp（尤其是 t1/t2）。

### 实测速度对比（参考独立对比报告）

| 任务 | llama.cpp MTP4/128K + KV q8_0 | vLLM-MTP (GPTQ-INT4) | 备注 |
|------|-------------------------------|----------------------|------|
| t1 (HTML) | 30.8 t/s | ~72 t/s | vLLM 快约 2.3x |
| t2 (SVG)  | 36.4 t/s | ~77 t/s | vLLM 快约 2.1x |
| t3 (长 agent) | 28m23s | 31m48s | 差距很小 |
| t4        | 3m24s | 1m51s | vLLM 较快 |
| t5        | 22m13s（完成） | 崩 2/2 | llama.cpp 完胜 |

> 注意：vLLM 的高分多数来自**短上下文单发测试**（2400 token 截断），而 llama.cpp 成绩是完整 128k agent 长链一次跑满 5/5 的数据。

### 主要原因

1. **量化方式差异（最主要因素）**
   - vLLM 使用 **GPTQ-INT4**（对称，group=128，配合 MTP-BF16 draft）。
   - llama.cpp 使用 **Q4_K_M** GGUF。
   - Intel Arc B70 的 XMX 整数引擎对 GPTQ INT4 有更成熟的内核支持（vllm-xpu-kernels 做了针对性优化）。

2. **引擎架构与调度差异**
   - vLLM：PagedAttention + 连续批处理 + `VLLM_XPU_ENABLE_XPU_GRAPH=1` + 较激进的 batching 参数。
   - llama.cpp：原生 SYCL 实现，内存管理和调度目前更保守。

3. **MTP 实现的优化程度**
   - vLLM 侧使用了 cookbook 提供的专门 MTP patch，对投机解码的边界处理和图捕获进行了优化。
   - llama.cpp 的外部 MTP（`--spec-type draft-mtp`）实现相对更新，吞吐优先级目前不如 vLLM 激进。

4. **测试负载不同**
   - 短 prompt + 短生成时，vLLM 的优势非常明显。
   - 进入真实长上下文、多轮工具调用、上下文持续增长的 agent 负载后，速度差距大幅收窄（t3 几乎持平）。

### 现实权衡

- **vLLM 优势**：单发/中短任务吞吐更高，首 token 更快。
- **llama.cpp 优势**：在完整 dsh agent 长链任务上**稳定性明显更好**（目前唯一能单批次跑通全部 5 个任务的方案）。vLLM-MTP 在 t5 这类重负载下出现过多次崩溃。
- KV q8_0 + llama.cpp 使得 128K + MTP4 能在 B70 上稳定运行，这是当前 vLLM 方案在同样负载下尚未完全解决的问题。

**总结**：vLLM 在“快”上仍有优势，主要来自量化内核和 serving 栈的成熟度；但在“稳”（尤其是复杂长 agent 负载）上，llama.cpp MTP4 + 128K + q8_0 目前是 B70 上更可靠的选择。
