### 3.1 ⚠️ Config defect found: two golden variables were silently ignored

`docs/GOLDEN-CONFIG.md` §3 specifies `LLAMA_ARG_SPEC_DRAFT_TYPE_K` / `LLAMA_ARG_SPEC_DRAFT_TYPE_V`.
**Those names do not exist in this build, or in the production baseline.** Verified by grepping the
actual env-var strings out of the shipped libraries on both images:

| Build | Variables present |
|---|---|
| baseline `d7f30320…` (v0.4.1) | `LLAMA_ARG_SPEC_DRAFT_CACHE_TYPE_K`, `LLAMA_ARG_SPEC_DRAFT_CACHE_TYPE_V` |
| candidate `a7106ff2…` (v0.5.0) | `LLAMA_ARG_SPEC_DRAFT_CACHE_TYPE_K`, `LLAMA_ARG_SPEC_DRAFT_CACHE_TYPE_V` |

The arg is declared in `llama.cpp/common/arg.cpp` as
`{"--spec-draft-type-k", "-ctkd", "--cache-type-k-draft"}` with
`.set_env("LLAMA_ARG_SPEC_DRAFT_CACHE_TYPE_K")` — note the CLI flag and the env var differ, and the
doc recorded the flag-shaped name.

**Consequence:** `LLAMA_ARG_SPEC_DRAFT_TYPE_K/V` is silently ignored (no warning, no error), so a run
that delivers the draft KV through *those env-var names* falls back to the **f16 default** — confirmed
by launching that way and reading the log back (`cache_k=f16, cache_v=f16`, draft KV buffer
**512.00 MiB** instead of **272.00 MiB**).

**This is a latent config bug, not a defect in any past measurement.** Every recorded baseline run
predates the env-var form entirely and passed the draft KV as a **flag**:

```bash
# start-v041-prodparams.sh (the v0.4.1 production-params run)
--spec-draft-type-k q8_0 --spec-draft-type-v q8_0
```

`--spec-draft-type-k` is the real CLI flag name — only the *env var* is spelled
`…CACHE_TYPE_K`. So the baselines ran draft KV at **q8_0** all along. Verified against the baseline's
own server log, not inferred from docs:

```
test-v041/server-v041.log:  spec common_specu: - gpu_layers=-1, cache_k=q8_0, cache_v=q8_0, ...
```

**Therefore §4.2 is a clean, matched-precision comparison** — baseline, pass 1 and pass 2 all ran
draft KV `q8_0` (272 MiB), and this run's corrected variable names simply keep it that way under the
env-var form. No confound; §4.4 item 1 is withdrawn.

**Docs fix — DONE (2026-09-23).** `GOLDEN-CONFIG.md` §3, `docker-compose.yml` and
`examples/qwen27b-server.sh` now all use `LLAMA_ARG_SPEC_DRAFT_CACHE_TYPE_K/V`, and §3 carries an
explicit warning explaining the flag/env naming mismatch. §6 of `GOLDEN-CONFIG.md` still needs
re-baselining against the corrected config (see §8).

### 3.2 `-v` is now a container setting (`DEBUG_FLAG`), not a step to remember

`-v / --verbose / --log-verbose` is the **only** llama-server argument with no `.set_env(...)`
mapping in `common/arg.cpp`. **No environment variable upstream will enable it** — `ENV
LLAMA_ARG_VERBOSE=1` is silently ignored, and `LLAMA_ARG_LOG_VERBOSITY` sets a numeric threshold
rather than emitting the per-request `print_timing` lines. During this run that cost a restart cycle:
the first launch had no `-v`, producing a 13-line log and zero acceptance data.

The `server` Dockerfile stage now injects it from the environment:

```dockerfile
ENV DEBUG_FLAG=""
ENTRYPOINT [ "/bin/sh", "-c", "exec /app/llama-server $DEBUG_FLAG \"$@\"", "--" ]
```

Verified against the released `sha256:a7106ff2…` image (`/bin/sh` = dash):

| `DEBUG_FLAG` | resulting argv |
|---|---|
| unset / `""` | `--model … --ctx-size …` — **no extra argument** |
| `-v` | `-v --model … --ctx-size …` |
| `-v --log-colors off` | `-v --log-colors off --model …` |
| `-v`, no user args | `-v` |

End-to-end with the real binary: `DEBUG_FLAG=-v` produced **6100 log lines and 4 `print_timing`
records** for a single request, versus **13 lines and 0 records** without it — exactly the data whose
absence makes agent-task acceptance unrecoverable. `docker-compose.yml` wires it as
`DEBUG_FLAG=${DEBUG_FLAG:-}`; `examples/qwen27b-server.sh` gained the same variable for the bare-metal
path. A `--` on the `docker run` command line is **not** needed and actively breaks boot (llama-server
reads it as an option name → `error while handling argument "-c": stoi`, ExitCode 1) — documented in
`GOLDEN-CONFIG.md` §2.1.

## 7. Environment notes worth recording

- **`-v` has no environment-variable equivalent in this build.** `llama.cpp/common/arg.cpp` declares
  `{"-v", "--verbose", "--log-verbose"}` with **no** `.set_env(...)`. `LLAMA_ARG_VERBOSE` and
  `LLAMA_ARG_LOG_VERBOSITY` do different things (the latter sets a numeric threshold and does not
  enable the per-request `print_timing` lines). The golden config must pass `-v` as a flag. Launching
  without it silently produces a 13-line log and **permanently loses agent-task acceptance data** —
  this cost one restart cycle here.
- **`wc -l` is a useless log-window marker under `-v`**: a single request body is one enormous line, so
  a 690 k-line log reports as `lines=1` from a naive count in some quoting contexts. Use the
  `print_timing` count plus the byte count as the window boundary.
- **`chown`/`chmod` on a container-shaped test home is one-way.** A `dsh-home` mounted into the harness
  (uid 1000 = `nobody` on the host) can be chowned by the container but **not** reclaimed by the host
  user, and the whole tree then fails `chmod`/`rm`. Create the test home world-writable (`chmod 777`)
  before the first container start, and move it aside rather than editing it in place if it goes wrong.
