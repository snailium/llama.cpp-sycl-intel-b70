## III. Final conclusions

1. **MTP4 + 128K + q8_0 is the vertex config** on B70 — 5/5 text + vision usable, TTFT minimal, decode 36–41 t/s, long-chain acceptance 0.50+.
2. **llama.cpp is the only backend that reliably completes the full agent suite** on B70 (vLLM crashes on long T5).
3. **Vision** reaches high quality (on par with dual-3060 27B) but is slow — choose it when quality matters over speed.
4. Single-digit OCR is an **inherent Qwen3.8-family shortcoming** (shared across backends; verify by crop-and-zoom).
5. **Status:** the current best/complete recommended config. For higher single-shot speed consider vLLM or lower context, at the cost of stability/context.

## IV. Why vLLM-MTP "looks" faster

Same MTP4/128K nominal setup: vLLM single-shot decode is clearly higher.

| Task | llama.cpp MTP4/128K q8 | vLLM-MTP (GPTQ-INT4) | Note |
|------|------------------------|----------------------|------|
| T1 HTML | 30.8 t/s | ~72 t/s | vLLM ~2.3× |
| T2 SVG | 36.4 t/s | ~77 t/s | vLLM ~2.1× |
| T3 long agent | 28m23s | 31m48s | gap small |
| T4 | 3m24s | 1m51s | vLLM faster |
| T5 | 22m13s (done) | crash 2/2 | llama.cpp wins |

> Note: many vLLM figures come from **short-context single-shot tests (2400-token truncation)**, whereas llama.cpp here is the full 128k agent suite run 5/5 in one pass. Critically, **vLLM-MTP never completed all five tasks in a single batch** — its numbers are stitched together from a 2026-08-19 single-shot batch (T1/T2/T4/T5) and a 2026-08-20 agent rerun (T3/T4); llama.cpp is the only backend that passes all five in one run.

**Main drivers:**
1. **Quantization:** vLLM uses GPTQ-INT4 (native, mature XMX kernel support in vllm-xpu-kernels); llama.cpp uses Q4_K_M GGUF.
2. **Engine/scheduler:** vLLM PagedAttention + continuous batching + `VLLM_XPU_ENABLE_XPU_GRAPH=1`; llama.cpp SYCL is more conservative.
3. **MTP maturity:** vLLM uses the cookbook MTP patch with graph capture; llama.cpp's external MTP is newer and less throughput-aggressive.
4. **Load shapes:** vLLM shines on short prompt+short generation; the gap shrinks on real long multi-tool agent chains (T3 near tie).

**Practical trade-off:** vLLM wins on *raw speed* (mature quant kernels + serving stack); llama.cpp wins on *stability* under complex long agent loads (currently the only 5/5-in-one-pass option). On equal 128k+agent loads where vLLM still crashes, llama.cpp MTP4/128K/q8 is the more reliable choice.
