**Fill-rate caveat (important).** For agent tasks most prompt tokens are *cache hits*
(`cacheReadTokens`) and are not reprocessed, so only the non-cached `inputTokens` are real prefill
work. Requests with a very small new-token count are dominated by fixed TTFT overhead and drag the
all-request weighted average down. The table therefore reports the **large-prefill weighted rate**
(requests with ≥1000 new tokens) for t3/t4/t5, which is the comparable figure. Both derivations:

| Task | all-request weighted | large-prefill weighted | requests ≥1000 new tok |
|---|---|---|---|
| t3_security | 456.5 | 505.3 | 7 of 14 |
| t4_hostinfo | 203.8 | 426.5 | 1 of 2 |
| t5_snowfall | 319.0 | 471.4 | 8 of 34 |

t4's all-request figure (203.8) is an artifact, not a regression: one of its two requests carried
only **125 new tokens** against a 4.0 s TTFT, i.e. almost pure overhead.

Read honestly:

- **Text decode is within noise of baseline** everywhere (−1% to +4%). That is the expected result —
  decode is memory-bound and a userspace-stack bump should not move it.
- **t1/t2 are effectively identical**, including draft acceptance (0.755 vs 0.744; 0.889 vs 0.897).
- **Some fill rates are higher** on t5/V1/V2/V3. Fill on cached prompts is sensitive to how many new
  tokens each request happened to carry and to cache-hit geometry, and the baseline's own numbers
  move 298–492 across agent tasks for the same reason. I would **not** claim the driver bump made
  prefill faster; I would claim only that *no regression* was measured and the spread is consistent
  with request-mix noise.
- **V3 decode 40.1 → 34.8 (−13%)** is the one cell that looks like a real drop, but it is a single
  short vision request (410 output tokens, speculative decoding active) and is inside the run-to-run
  spread this setup has historically shown. One sample does not establish a regression; it is
  flagged, not concluded.
- **t4 fill −13%** is the small-denominator artifact described above (n=1 large request).

No number in this report is extrapolated beyond what was measured.

## 5. Numbers that could NOT be measured

Stated plainly, per the "no extrapolation" rule:

1. **Draft acceptance for t3/t4/t5 — NOT MEASURED.** The server logs verbose `draft acceptance`
   lines, but they live only in the candidate container's log. I removed the test container to free
   the GPU **before** extracting those windows, and Docker log storage is deleted with the container;
   an explicit check for an orphaned log directory found none. The user was offered a re-run of

   extra downtime. Baseline values for reference only: t3 0.532, t4 0.809, t5 0.812.
2. **Per-task draft acceptance for V1/V2/V3 — PARTIALLY measured.** Two acceptance lines were
   captured in the vision window (0.509 = 58/114 and 0.596 = 286/480), but which of V1/V2/V3 each
   belongs to cannot be recovered now that the log is gone. Reported as ambiguous rather than guessed.
3. **t4 prefill vs baseline is not a like-for-like comparison.** The baseline's t4 request mix is not
   recorded in `GOLDEN-CONFIG.md`, so a 2-request window cannot be compared to it honestly.

Draft acceptance **was** measured for t1 (0.755) and t2 (0.889).

## 7. Findings to action

### 7.1 The production container has drifted from the documented golden config

`docs/GOLDEN-CONFIG.md` §3 and **every** repo mirror (`examples/qwen27b-server.sh` L56,
`docker-compose.yml` L62, `docs/B70-TUNING.md`, `docs/B70-SYCL-KNOWLEDGE.md`) specify
`--spec-draft-n-max 3`, and §3's rationale explicitly says *"MTP3 beats MTP4 on agent workloads"*.

The live production container `b70-sycl` is running **`--spec-draft-n-max 4`**:

```
docker inspect b70-sycl --format '{{json .Config.Cmd}}'
  … "--spec-draft-n-max", "4", …
```

This test used **n-max 3**, i.e. the documented golden, which is the correct thing to validate a
release candidate against. But production was not running what the single-source-of-truth document
says, and the last A/B (2026-09-01) found **MTP4 costs 25–34 % wall-clock** on agent tasks.

**Resolved 2026-09-20** — production was corrected to `--spec-draft-n-max 3` and the stale canonical
compose was re-synced; see §9.2 and §9.3.

### 7.2 Level Zero version in the issue does not match the image

The issue states **Level Zero 1.32.0**; the image ships **`libze_loader.so.1.28.6`**. This is very
likely the *loader package* vs the *Level Zero API/spec version* (1.32.0 is the spec level the
driver targets), but the two are reported as the same field, so the build metadata is ambiguous.
Confirm and, ideally, have CI report the loader soname explicitly.
