### 2.1 ⚠️ `DEBUG_FLAG` is NOT yet available in this image

The `-e DEBUG_FLAG=-v` mechanism added in commit `f0cf4df` lives in the **Dockerfile source**, and
the released image was built **before** that change. Its entrypoint is still the old one:

```
$ docker inspect … --format '{{json .Config.Entrypoint}}'
["/app/llama-server"]
```

So `DEBUG_FLAG` is **inert** on this digest: the container accepts the variable and silently ignores
it, producing a 13-line log and no verbose detail. This pass therefore passed `-v` as a real
argument, exactly as pass 1 did.

**This corrects an ambiguity in the previous message.** The `DEBUG_FLAG` semantics were verified by
*simulating* the new entrypoint inside the released image (`--entrypoint /bin/sh`), which proves the
wrapper logic is correct — it does **not** mean the released image already has the capability. Any
future validation run against this digest must still pass `-v` explicitly; `DEBUG_FLAG` only takes
effect once an image is rebuilt from `f0cf4df` or later.

**Process consequence (worth keeping):** the missing `-v` was caught by the pre-flight check reading
`docker logs | wc -l` (13 lines), not by a failed request. Both passes needed a relaunch for this
reason, and the first pass lost a cycle to it as well.

### 5.1 The router did NOT self-heal — SMG restart was required

This is the failure mode the procedure warns about, and it reproduced for real here. After
`b70-sycl` was restarted:

```
worker  18080  direct /health : {"status":"ok"}          <- worker is fine
worker  18080  direct infer   : content "ok"             <- and it really infers
/workers       18080          : is_healthy=false, status=failed   <- but SMG disagrees
/workers       18090          : is_healthy=true,  status=ready
```

A routed request still succeeded (SMG failed over to the XTX worker on 18090), so a casual check
would have declared the restore complete — **while the B70 worker was actually excluded from
routing**. Waiting did not clear it.

`docker restart smg` cleared it immediately:

```
/workers after restart
  18090  healthy=true  status=ready
  18080  healthy=true  status=ready
```

and a routed request then returned a real completion (`content='ok'`, no 503).

**Post-restore state**: all three containers `running`, `RestartCount=0`, `OOMKilled=false`,
production back on the exact baseline digest `sha256:d7f30320…`.

**Lesson worth keeping**: on this platform, "routed request succeeds" is **not** sufficient evidence
of a full restore when two workers back the same model — failover masks a dead worker. `/workers`
must be checked for **every** worker, and if one reads `failed` while its `/health` is `ok`, restart
SMG.

## 6. Answer quality

### 6.1 ⚠️ t5 is WRONG on this pass — unit error, plus a window error

The two passes produced **different answers**, which triggered a direct check against the source.

| Pass | Answer | Window | Source |
|---|---|---|---|
| 1 | **258.6 mm** | 327 days (full task window) | ECCC official API, daily `TOTAL_SNOW` |
| 2 | **217.0 cm** | 4 months only | two secondary sites, monthly values |

I re-derived the authoritative figure straight from the ECCC API
(`api.weather.gc.ca/collections/climate-daily`, `CLIMATE_IDENTIFIER=6106001`):

```
days with numeric value : 326      TOTAL : 258.6 mm   ( = 25.9 cm )
monthly: 2025-11 32.5 | 2025-12 54.6 | 2026-01 81.6 | 2026-02 48.3 | 2026-03 41.0 mm
```

**Pass 2's monthly numbers are all correct** (32.5 / 54.6 / 81.6 / 48.3), and their sum is
**217.0 mm**. But pass 2 reported them as **217.0 cm** — a **10× unit error**. `TOTAL_SNOW` is
reported in millimetres; 217.0 mm is 21.7 cm.

Pass 2 also made a second error: it stated "该时段恰好覆盖四个完整自然月" (the window covers exactly
four complete months) and excluded March, but **March 2026 contributed a further 41.0 mm** within the
task's window. So pass 2 both mislabelled the unit and truncated the window.

It also silently substituted weaker sources: it reported that the ECCC endpoint needed JS/session
interaction and fell back to two secondary sites, whereas pass 1 queried the official API
successfully (finding the `stn_id` filter broken and using `CLIMATE_IDENTIFIER` instead). Pass 2's
claim that the official interface is unreachable by plain HTTP is **not correct** — this report's own
verification script fetched it directly over HTTP in this same environment.

**Assessment**: same model, same digest, same config, two materially different answers to a
numerical question, one of them 10× off. This is **run-to-run answer variance**, and it is the
strongest argument in either pass for treating t5 as a *flaky* quality signal rather than a stable
one. It does not indicate a backend fault — the backend produced well-formed, complete, sourced
answers both times — but it does mean a single green t5 run should not be read as proof that the
numeric path is reliable.
