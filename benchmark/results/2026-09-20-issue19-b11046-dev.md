Read honestly:

- **Both short direct-call tasks are effectively identical** to baseline (fill −5%/−1%, decode −2%/+1%,
  acceptance 0.728 vs 0.755 and 0.897 vs 0.889). t1's −5% fill is a 43-token prompt: 61.8 vs 64.9 tok/s
  is a 45 ms difference on a single prefill, i.e. inside measurement noise, not a signal.
- **All three vision tasks are within noise or slightly better** (decode +8%/−0%/+5%).
- **t4 fill +25% and t5 fill +16%** are *not* claims I would make as improvements. The #18 run's t4 had
  only 2 large requests and t5 had 8 of 34; this run had 2 of 47 and 5 of 59 — a different request mix
  on a cache-sensitive metric. Both baseline and candidate numbers for the same nominal task move by
  tens of percent purely from request geometry (see §4.1's all-request vs large-prefill split, which
  spans 221→533 on t4 alone). I claim only that **no prefill regression was measured**.
- **t5 decode −9%** and **t4 decode −5%** are the largest drops. Both are weighted across a *much*
  larger request count than the baseline run (59 vs 34; 47 vs 2), so the weighting basis differs;
  the short-context decode rate that is directly comparable (t1/t2, V1-V3) is unchanged. Flagged, not
  concluded.
- **t3 TTFT 4.74 → 9.13 s** is the one cell that moved a lot. It is a median over only 14 requests
  whose individual TTFTs range 1.39-32.17 s and scale directly with new-token count (the largest
  request, 17 125 new tokens, took 32.17 s). The baseline's t3 request mix is not recorded, so this is
  not a like-for-like comparison; t3's prefill *rate* (505.6 vs 505.3) is unchanged, which is the
  metric that is actually mix-independent here.

No number in this report is extrapolated beyond what was measured.

## 5. The one real incident: t5's first attempt was an agent loop, not a backend fault

t5's **first** attempt ran >40 minutes without producing an answer. I investigated rather than
assuming a hang, per the "stuck requires two pieces of evidence" rule, and found:

- The backend was **healthy and working throughout**: `RestartCount=0`, ~100 % container CPU,
  53 803-token prompts being served, and `slot print_timing` acceptance **0.988** with
  `acc per pos = (1.000, 1.000, 0.964)` — i.e. speculative decoding performing excellently.
- The dsh session log showed **432 tool calls, 433 requests, 90 632-token context, 47 593 output
  tokens**, with the last ~8 calls being *the same* `curl https://climatedata.ca/wp-json/cdc/v3/variable…`
  command. The fetched page returned a JS shell ("This page contains no extractable data"), so the
  model kept retrying an unproductive source.
- The `dsh-repeat-tool-breaker` plugin fired `REPEAT_TOOL_BLOCKED` repeatedly but did not stop the loop,
  because successive commands differed in trailing content.

**This is an agent/harness + data-source-availability failure, not a B70 backend defect.** It is
directly analogous to issue #18's empty-mount t3 incident. I killed the loop, preserved its session
log (`test-issue19/t5_session_partial/`), and **re-ran t5 once from a fresh `DSH_HOME`**. The retry
succeeded (§4.1) by finding a different source and cross-validating it. Only the successful run is
reported in the results table; the loop's metrics are not backend results.

Because the first attempt was aborted by me rather than by the backend, the candidate's
`RestartCount` stayed 0 and no container restart occurred — confirmed above.

## 8. Verdict

**The suite is fully green: 8/8 tasks passed, zero crashes, zero restarts, no cross-card damage, and
no memory-splitting.** Fill, TTFT and decode are within measurement noise of the baseline on every task
where the comparison is genuinely like-for-like, and the Intel userspace stack is byte-identical to the
promoted baseline — so the only variable under test is the llama.cpp commit (`b29c606` → `60081bb`),
and it introduced no measured regression.

**Decision: PROMOTE to the `dev` channel. Do NOT move `stable`.**

This is the "green but not worth shipping to stable" case, stated plainly rather than hidden:

- The issue itself labels this a **dev weekly build** ("Development snapshot. Use at your own risk.")
  and the action is `reopened` on the **dev** tag namespace. It was never proposed for `stable`.
- It passed every check I can run, but it carries an **unexplained llama.cpp commit bump** with no
  stated reason in the issue body (`**Reason**:` is empty) and **no upstream PR description was
  supplied** to justify the change. Promoting a commit with no stated rationale over a
  just-promoted, fully-validated stable is not a risk worth taking for zero measured gain.
- The measured result is **parity, not improvement**. Parity does not justify moving `stable`; it does
  justify publishing the dev artifact for the channel it was built for.

So: publish/tag the dev artifact; leave `stable` at `sha256:d7f30320…`.

What would change this decision: a stated reason for the llama.cpp bump plus a repeat run showing a
real, mix-controlled gain (e.g. a fixed-prompt A/B on decode rate), or an upstream fix that this
commit is known to carry.

### 8.1 Numbers that could NOT be measured

Stated plainly, per the "no extrapolation" rule:

1. **Nothing is missing from the three mandatory metrics for any task.** Unlike #18, draft acceptance
   was captured for **all eight tasks** (t3/t4/t5 from `slot print_timing` windows keyed to log-line
   markers recorded before each task; t1/t2/V1-V3 from response-body `timings`), because the log was
   extracted **before** the container was removed.
2. **t3/t4/t5 acceptance is "requests that emitted `slot print_timing`"**, not necessarily every
   request the task issued — the service does not run `-v` per-request `timings` for the harness client.
   Line counts are stated in §4.1 (15, 4 and 61 lines respectively).
3. **Reasoning/thinking token counts**: not applicable — `--reasoning off` plus
   `enable_thinking:false` was in force, and `reasoning_content` was absent on every direct call and
   the restoration check.
4. **t4's `completion_tok` is a lower bound** (1180+): its 47-request session log exceeds what I summed
   for the headline cell, and the prefill/decode figures are the weighted ones in §4.2.
