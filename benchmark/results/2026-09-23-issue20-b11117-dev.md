### 1.2 The Level Zero discrepancy is FIXED — this is a stack change, not just a llama.cpp bump

`docs/LEVEL-ZERO-VERSION-DISCREPANCY.md` root-caused a packaging bug: every issue body claimed
"L0 1.32.0" (the version CI *intended* to install) while the shipped image actually contained
`libze1 1.28.6`, because the oneAPI install stage silently displaced the CI-pinned Level Zero
packages. Issues #18 and #19 both shipped `1.28.6` and carried the discrepancy forward.

**This image ships `1.32.0`.** Verified directly from the image:

```
$ dpkg -l | grep libze1
ii  libze1   1.32.0   amd64   oneAPI Level Zero
$ ls -la /usr/lib/x86_64-linux-gnu/libze_loader.so*
lrwxrwxrwx  libze_loader.so.1 -> libze_loader.so.1.32.0
-rw-rwxr--  libze_loader.so.1.32.0   (1036264 bytes, Jun 26 23:49)
```

The same check on the baseline `d7f30320…` image returns `libze1 1.28.6-1~26.04~ppa1` /
`libze_loader.so.1.28.6`, confirming this is a real change and not a reporting artefact.

This is a **bigger change than a llama.cpp build bump** and gets its own line: the loader is the
component that sits between the SYCL runtime and the GPU driver, so a loader swap can change
allocation behaviour and error surfaces. The issue body's "Image actually contains: libze1 `unknown`,
loader `libze_loader.so.1.32.0`" is now accurate — `libze1` reads `1.32.0`, not `unknown`.

**Consequence for the report:** the comparison below is *not* a clean llama.cpp-only A/B (unlike
issue #19, which was). Both the llama.cpp build and the Level Zero loader moved. Any difference
measured here is attributable to the pair, and no measured difference was large enough to need
disentangling.

### 4.4 One incident: t3's first attempt was a harness mount failure, not a backend fault

t3's **first** attempt produced a review of an **empty directory**. The model reported it honestly —
"`/workspace/mqtt2ha` exists but is **completely empty** — there is no code to review" — rather than
inventing findings, which is the correct behaviour.

Root cause was in **my runner**, not the backend: the `git clone` target was under `/tmp`, and on this
control host **`/tmp` is a per-shell ephemeral tmpfs** — each `bash` invocation gets a fresh mount, so
the clone had vanished before `docker run` executed. Verified directly:

```
$ docker run --rm -v /tmp/mqtt2ha-test:/workspace/mqtt2ha:ro ... -c 'ls /workspace/mqtt2ha | wc -l'
0
$ docker run --rm -v <workspace-path>/mqtt2ha:/workspace/mqtt2ha:ro ... -c 'ls /workspace/mqtt2ha | wc -l'
23
```

Re-run from a persistent workspace path with a fresh `DSH_HOME` and a mount pre-check (`23 files`)
gave the real review reported in §4.1: 12 requests, 47 946 prompt tokens, findings citing
`web.go`, `websec.go`, `store.go`, `yamlstore.go`, `mqtt.go`, `Dockerfile` with line numbers.

Only the successful run is reported in the results table. The backend was healthy throughout both
attempts (`RestartCount=0`); the empty-mount run's metrics are not backend results.

## 8. Verdict

**The suite is fully green: 8/8 tasks PASS, with all three mandatory metrics present for every task
and draft acceptance recovered for 99/99 agent requests.**

- `RestartCount=0`, `OOMKilled=false`, zero crash/OOM/device-loss signatures across the full run.
- No memory-buffer splitting; the main model loaded as a single 17402.38 MiB allocation.
- Every prefill rate within ±3 % of baseline; decode flat-to-better on the comparable tasks;
  acceptance equal or better everywhere a baseline number exists.
- Production `b70-sycl` restored and verified **end-to-end through SMG** — a routed request returns a
  real completion, so this is not a "healthy but 503" restore.

**Promote decision: promote to the `:dev` channel.** The build is a clean pass and there is no
measured regression to justify withholding it.

**Do not move `:stable`.** Two reasons, stated plainly:

1. **The change is not understood as well as it looks.** This candidate moves *two* things at once —
   the llama.cpp build (b11046 → b11117) and the Level Zero loader (1.28.6 → 1.32.0). Issue #19's
   candidate was a llama.cpp-only bump over an otherwise byte-identical stack, which is why its
   parity result was easy to trust. Here the loader swap is the more consequential change and this
   single run, while clean, is one data point. It is also the first image in which the
   `LEVEL-ZERO-VERSION-DISCREPANCY.md` fix is actually present, so it is the first build exercising
   L0 1.32.0 on this card in this configuration.
2. **The issue states no reason for the bump** — the "Reason" field is empty and the body says only
   "Development snapshot. Use at your own risk." Consistent with how issue #19 was handled, a
   parity-plus-no-stated-reason bump belongs on the dev channel until someone asks for it on stable.

What would change this: a second clean full-suite pass on this same digest (to rule out a one-off),
plus a stated reason to adopt the loader bump in production — at which point this digest is a
reasonable `:stable` candidate, with `sha256:d7f30320…` remaining the rollback point.
